3. Remaining gap — and it lands on IRS specifically

The reviewer identified a combination of two individually reasonable decisions that produce a silent miss with a PASS verdict:

GAP (a)

Unique columns skipped — return None ships real PII

Any column in any unique index returns None — kept verbatim. The reasoning is that a shape-collapsing transformer on a unique column can emit duplicates and break the restore, and that "these are identifiers/sequences, not free PII." The restore concern is real. The characterisation is what doesn't hold for a registration system — a registration system's natural unique keys are its PII: participant email, phone, registration number, government ID.

Suggested fix (review) Don't skip — use an injective transformer for unique text columns (Hash, or greenmask's deterministic engine) instead of return None. Injective means distinct inputs stay distinct, so the unique index still builds — which is the exact constraint that motivated the skip. You get masking and restore safety, rather than trading one for the other.
Response — Done exactly as suggested

Replaced the return None for unique text columns with the greenmask Hash transformer. Hash is deterministic per input → injective (distinct inputs map to distinct outputs), so the unique index still builds without collision. This gives masking and restore safety, exactly as the review describes.

The change is narrow: the unique check now fires after all existing structural exemptions (FK → None, selection → None, bytea → None, json/jsonb → None, _SKIP_COLUMNS / _id / _state → None). So it only fires on text/varchar unique columns — the exact case the review identified. Integer and other non-text unique columns are still kept (they're structural, not PII).

The business-name special case (_NAME_IS_BUSINESS_TABLES) already handled unique text names correctly — it uses RandomCompany with engine=hash for unique columns (commit 46cdf20 era). The new unique-Hash code path fires for all other unique text columns that weren't special-cased — which is the gap the review found.

  • Updated the transformer_for() docstring to document the injective Hash rationale.
  • Updated the snapshot_schema() docstring to document the unique column treatment.
  • Updated the module-level docstring and the generated profile header comment.

GAP (b)

Scan covers 6 hardcoded core tables

The H1 scan checks six hardcoded tables (res_partner res_users hr_employee res_company crm_lead hr_applicant) — all Odoo core. No custom or addon tables. For IRS, the PII lives substantially in prs-backend's own models. A hardcoded list is guaranteed to be wrong for every non-core app.

Suggested fix (review) Derive the table list from the generated profile — every table with a PII-classified column — rather than hardcoding. Or sample all text columns across all tables with a LIMIT per column. Keeps the verifier in step with the masker automatically as addons change.
Response — Done as suggested (derive from profile)

Implemented the review's primary suggestion: the scan table list is now derived from the generated greenmask profile. The masker parses /tmp/greenmask.yml (the rendered config) with PyYAML and extracts every table name from the dump.transformation list — exactly the tables the masker applied transformers to. This keeps the verifier in step with the masker automatically as addons change.

Additionally:

  • FK-forced-back tables (H7, see below) are added to the scan list because they ship with real data.
  • Fallback: if the profile can't be parsed (e.g. the baked default profile path that doesn't have a transformation list we can introspect), the scan falls back to the original 6 core tables. This is logged so the operator knows the fallback is active.

The review's alternative suggestion ("sample all text columns across all tables with a LIMIT per column") would be broader but slower and would produce more false positives on structural tables. Deriving from the profile is more precise — it scans exactly the tables the masker decided needed masking — and is the review's primary recommendation.

4. Canaries — the objection is solvable

COUNTER-PROPOSAL

Seed canaries into the restored temporary instance, not the source DB

Your reasoning was that seeding canaries requires writing to the source DB, which conflicts with the read-only source principle. That's sound as stated — but it assumes the canaries go into the source. Seed them into the restored temporary instance instead. Per H6 the pipeline should be restoring a snapshot to a throwaway instance and masking from that; that instance is writable by definition and is not production. Insert canary rows immediately after restore, before greenmask runs, then assert those exact values are absent from the masked output.

This closes precisely the gap you identified yourself — a shape-preserving transformer silently failing to apply, where the value survives but the pattern scan can't tell because the shape is unchanged. The pattern scan and the canary catch different failure classes; neither substitutes for the other.

Response — Done (counter-proposal accepted)

The review is correct: the canary goes into the restored temporary instance (the writable target DB the masker restores into), not the source DB. This sidesteps the read-only source principle entirely — the temp instance is not production and is writable by definition.

Implementation (step 6a, before the post-mask scan):

  • Creates a dedicated _synth_canary table (not a real Odoo table, so it doesn't interfere with Odoo's schema or FK integrity).
  • Inserts one canary row with known PII-shaped values: canary.test.senthil@example.canary (email), +919876543210 (phone), Canary Senthil Nathan (name), Canary secret: AKIA-TEST-CANARY-TOKEN-XYZ123 (secret-shaped text).

Verification (step 6b, check 4): After the pattern scan, the masker asserts that the exact canary values are absent from the masked DB. If any survive, the run FAILs — it means a transformer silently failed to apply (shape-preserving failure: the value kept its shape but should have changed). This catches the failure class the pattern scan can't detect, exactly as the review describes.

Cleanup: The canary table is dropped before the dump is produced (it's a verification artifact, not real data). If it survives into the dump, that's also a finding.

Toggle: CANARY_VERIFY (default true), wired through the pipeline (lib/backend/pipeline.py) and CLI (--canary-verify / --no-canary-verify).

The review is correct: when FK safety prevents emptying a high-volume table (a retained table has a FK into it), the table ships with ALL its real data — including binary attachments (ir_attachment.datas bytea) and mail message bodies that may contain PII.

Fix: two parts, working together:

The table is still present (rows intact for FK integrity) but its content columns are nulled/truncated. This is the same degrade-to-safe principle the review asked for: instead of shipping real data, ship empty content with the row preserved for FK constraints.

M1 — StrictHostKeyChecking=no on the bastion tunnel

StrictHostKeyChecking=no still present on the bastion tunnel — the path carrying production DB credentials.

Response — Done

Replaced StrictHostKeyChecking=no + UserKnownHostsFile=/dev/null with StrictHostKeyChecking=accept-new + a persistent known_hosts file (/tmp/ssh_known_hosts) in all three scripts that had the issue:

  • masker/entrypoint.sh — the bastion tunnel for the masker
  • discovery/entrypoint.sh — the bastion tunnel for the discoverer
  • scripts/launch_synthetic_source_db.sh — the synthetic source DB provisioning script (testing only, but fixed for consistency)

Why accept-new and not yes: the masker and discoverer run in ephemeral containers that may not have seen the bastion host before. accept-new auto-accepts the first-seen key (so the first connection succeeds without a pre-seeded known_hosts) but rejects changed keys on subsequent connections — this is MITM detection. yes would require a pre-seeded known_hosts file, which isn't practical for ephemeral containers that don't know the bastion host key ahead of time.

The known_hosts file is under /tmp (ephemeral per container run), so the first connection records the key and subsequent runs within the same container verify it. A bastion key rotation requires clearing /tmp/ssh_known_hosts — this is documented in the comment.
