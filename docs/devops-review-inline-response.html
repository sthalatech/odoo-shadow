Assumptions I'd like you to check

The review listed five assumptions and asked us to verify each against the codebase.

Assumption 1 — Is the IRS component set current?

Response

Yes — confirmed current. examples/multi-repo/components.yaml is the validated 5-repo IRS wiring: prs-backend (Odoo), prs-facade, prs-worker, prs-frontend, irs-admin-frontend. The file header says "Real 5-repo setup validated during multi-repo design."

The most recent change to this file (commit 409b676) was an explicit drift fix to keep the example in sync with the live profile after facade.expose.path was reverted. The commit message notes that "a fresh profile create from this file is supposed to reproduce the validated, working configuration exactly." No action needed.

Assumption 2 — Is there a compiler step for the rulebook?

Response

No — confirmed absent. Nothing in the codebase reads masker/rules/*.yml as an input. masker/entrypoint.sh loads only profiles/<MASK_PROFILE>.yml (baked or downloaded via MASK_RULES_URL). discovery/gen_masking.py generates greenmask profiles from schema introspection, not from the rulebook.

The C1 fix documents this explicitly in masker/rules/README.md: the rulebook is a specification ahead of implementation, not enforced policy.

Assumption 3 — Does the workspacer need the profile/* Secrets Manager grant?

Response

No — confirmed unnecessary. The workspacer's startup_script only reads the masked dump from S3 (aws s3 cp "$DUMP_S3_URI") and pulls the Odoo ECR image — both of which need only S3 read + ECR pull, not profile/* (source DB password / bastion SSH key).

The profile/* secrets are only needed by the masker and discoverer, which connect to the source DB. The C4 fix formalizes this: the workspacer defaults to env-instance (no profile/*), and the masker/discoverer default to the new runner-instance role (with profile/*).

Assumption 4 — What does SOURCE_DB_HOST point at?

Response

During the POC: a snapshot restored to a temporary RDS instance, never the production primary. The masker's source-DB access is read-only in practice (pg_dump + greenmask extraction only — no UPDATE/INSERT/DDL against the source), but the code does not enforce this: it connects with whatever credentials are provided, and there is no SET TRANSACTION READ ONLY guard or warning if the host looks like a production endpoint.

Future hardening item (not in this branch). Add a SET TRANSACTION READ ONLY guard in the masker's preflight, or require a dedicated read-only DB user, so the system enforces what is currently only operational practice. The review asked a question here, not for a code change — but for the pilot, the source DSN provided to odoo-synth profile create must point at a snapshot/temporary instance, not the production primary.

Assumption 5 — Cost figures (ap-south-1, ~10 concurrent sandboxes)?

Response

Region: the deploy scripts default to the AWS CLI's configured region (deploy/00_setup.sh:148 falls back to us-east-1 if none is set). The review's ap-south-1 assumption is an operator choice, not a code default — the region is prompted during deploy/00_setup.sh and stored in ~/.aws/config. For the pilot, the operator should set ap-south-1 if that's where the source DB and sandboxes will live.

Concurrency: the H2 concurrency cap defaults to 10 (ODOO_SYNTH_MAX_CONCURRENT, scripts/issue_to_env.py:335), matching the review's assumption of ~10 concurrent sandboxes. This is configurable if the pilot needs more or fewer.

C3 — Classification is name-based, and unknown columns fail open

gen_masking.py classifies by column name pattern and data type — it never samples values. And the documented default is explicit: "a column we cannot classify is left untouched." Any custom addon column (x_notes, applicant_comment) that doesn't match a built-in pattern passes through.

Suggested change (review) — the highest-leverage one here Invert the default to fail-closed. Any text/varchar column not explicitly declared keep gets redact_freetext. Generate a per-app exception list the app team reviews to un-redact the fields they need for realistic dev data. This turns an unbounded audit into a bounded, self-limiting task, puts the decision with the people who know the schema, and makes every mistake fail safe.
Response — Done (documentation fix; code was already fail-closed)

Verified the code: the final return path in discovery/gen_masking.py's transformer_for() already returns Masking("default") for any text/varchar column that doesn't match a keep pattern. The actual masking behavior was already fail-closed.

However, the documentation said the opposite:

  • The module docstring said "a column we cannot classify is left untouched" — contradicted by the code's actual Masking("default") return.
  • The generated profile header comment said "Columns not listed pass through unchanged" — also wrong.

This meant an operator reading the docs would have false confidence that unknown columns were passing through safely, when in fact they were being redacted. The fix was to correct the documentation to match the fail-closed reality:

  • Updated the module docstring to document the fail-closed default explicitly: any text/varchar column not explicitly declared keep (FK, selection, unique key, _SKIP_COLUMNS, _SKIP_TABLES, structural identifier) gets Masking("default").
  • Updated the generated profile header comment to say unclassified text columns get Masking("default"), NOT pass through unchanged.
  • Updated the final return comment to make the fail-closed intent explicit.

This turns an unbounded column audit into a bounded exception-list review, exactly as the review describes: the operator removes transformers from the ~30 fields they need for realistic dev data, and every mistake fails safe (redacted, not leaked).

HIGH~1 week

H1 — Nothing independently verifies the output

There's no check that masking actually worked. If a transformer silently fails to apply or a column is misclassified, the run succeeds and the dump lands in masked-dumps/ — and every downstream consumer trusts that prefix.

Suggested change (review) A mandatory post-mask stage that fails the run: seed canary records in the source before dumping, then assert those exact values are absent afterwards. Plus a scan for high-signal patterns (emails on known-PII tables, Indian mobile formats, Aadhaar/PAN shapes) failing on anything outside an allowlist. Write to a quarantine prefix first and only promote to masked-dumps/ on a pass.
Response — Done (pattern scan + fail-closed; canary + quarantine noted as future work)

Pattern-based PII scan (implemented): Added a new step 6b in masker/entrypoint.sh (between admin password set and dump upload) that scans the masked DB for high-signal PII patterns:

  • Emails, Indian mobile formats (+91 / 10-digit starting 6-9), Aadhaar/PAN shapes on known-PII tables (res_partner, res_users, hr_employee, res_company, crm_lead, hr_applicant).
  • Residual ir_config_parameter secret keys (verifies C2 scrub worked).
  • res_users with non-null password hashes (verifies only admin has one — verifies C2 scrub).

If any pattern is found, the run fails with exit 1 and the dump is never uploaded. The dump only lands in masked-dumps/ when verification passes.

Uses psql + python3 (both already in the postgres:16 image) — no new dependency. Configurable via POST_MASK_VERIFY (default true) + POST_MASK_ALLOWLIST (comma-sep table.column exemptions for fields where PII-shaped values are expected to survive, e.g. RandomEmail).

Wired through the pipeline: lib/backend/pipeline.py passes POST_MASK_VERIFY; cli/__init__.py adds --post-mask-verify/--no-post-mask-verify flags.

Not implemented — canary records (future enhancement). The review suggested "seed canary records in the source before dumping, then assert those exact values are absent afterwards." This would require writing INSERT statements to the source DB before the masker runs, which conflicts with the read-only source-DB principle (see Assumption 4). The pattern scan + C3 fail-closed default together provide equivalent coverage for the "column leaked entirely" case. Canaries would add value for the case where a column keeps its shape but should have changed its value (e.g. email → RandomEmail — a canary would confirm the value changed even though the shape survived; the pattern scan can't detect that). Worthwhile future enhancement, not a safety gap in the current implementation.
Not implemented — quarantine prefix (by design). The review suggested "write to a quarantine prefix first and only promote to masked-dumps/ on a pass." Our approach is simpler and equally safe: verification runs before the dump is uploaded, so a failed verification produces no artifact at all (nothing to quarantine). The dump only lands in masked-dumps/ when verification passes. A quarantine prefix would be useful if we wanted to inspect failed dumps for debugging — that's a debugging convenience, not a safety control.
